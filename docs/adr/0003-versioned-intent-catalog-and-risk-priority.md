# ADR-0003：用版本化意图目录约束分类与 Tool 权限

## Context

原实现的意图信号分散在条件分支与 Prompt 中。新增或修改意图时，产品边界、模型标签、Tool 权限和评测样本可能各自变化，无法回答“这个版本为什么这样路由、由谁负责、上线前验证了什么”。多诉求输入还可能因普通意图先命中而执行低风险 Tool，漏掉支付或投诉风险。

## Options

1. 继续维护 Prompt 和代码关键词：改动快，但没有统一业务资产、版本和权限边界。
2. 完全交给模型分类：长尾表达更灵活，但模型波动会直接影响路由，高风险与 Tool 权限难以硬约束。
3. 使用版本化 Intent Catalog，确定性安全信号优先，模型只处理目录未命中的长尾表达并接受目录约束。

## Decision

意图边界、正反例、风险级别、责任人、必需槽位和 Tool 白名单统一归属 `Intent Catalog`，而不是散落在 Prompt、关键词分支和评测脚本中；规则路由先识别支付/投诉等高风险信号，模型只处理目录未匹配的长尾表达，且输出必须被目录约束。同一轮允许一个主意图和多个次意图，高风险主意图抢占自动执行，但次意图进入摘要供人工继续处理。

选择该方案是因为它同时满足产品可运营、发布可回归和运行时安全三个目标。目录由业务负责人维护，分类结果携带目录版本，`finalize` 再校验“意图—Tool”权限，因此 Prompt 错误或模型误判不会自然获得额外 Tool 权限。

## Trade-offs / Consequences

- 修改意图边界需要升级目录版本并重跑混淆矩阵，而不是只改 Prompt。
- Tool 权限在目录和运行时双重校验，分类错误不能自然升级为写操作权限。
- 风险优先降低自动化覆盖率，但避免“查物流 + 修改银行卡”先执行普通 Tool；只保留单标签则会丢失用户其他诉求并降低人工接管质量。
- 目录规则无法覆盖所有长尾表达，所以保留受约束的模型回退；当前离线门禁主要证明确定性安全路由，生产模型仍需独立评测。
- 如果不建立目录，同一个意图可能在 Prompt、代码和测试中形成三套定义，无法稳定计算混淆矩阵，也难以审计一次错误 Tool 调用属于模型、业务边界还是权限配置问题。
