# ADR-0004：短期记忆只保存带治理属性的业务状态

## Context

多轮售后对话需要减少重复输入，但直接把聊天全文或模型摘要当作记忆，会把推测、旧订单信息和过期物流状态带到后续轮次。不同状态的有效期也不同：订单绑定可保留较久，物流事实几分钟后就可能变化，退货原因只能属于具体订单。

## Options

1. 每轮无状态：最安全简单，但连续追问反复索要订单号，体验和完成率差。
2. 保存全文或自由摘要：对话自然，但来源、作用域和时效不可验证，容易发生陈旧事实与跨订单串线。
3. 只保存结构化业务状态，为每项记录来源、置信度、作用域和 TTL，并明确纠正与失效规则。

## Decision

系统不把聊天全文或模型摘要直接视为短期记忆，只继承结构化槽位与 Tool 已验证事实；每个状态项必须携带来源、置信度、会话/订单作用域和过期时间。显式请求高于继承记忆，用户切换订单时旧订单的退货原因、已验证事实、上一意图和连续未解决计数立即失效。

选择该方案是因为售后对话真正需要继承的是少量可验证业务状态，而不是无限增长的文本。它保留“那什么时候到”“原因是尺码不合适”等连续体验，同时能解释每个值从哪里来、何时失效、为什么可以使用。Tool 事实只用于短期状态与审计；需要实时结论时仍重新调用受控 Tool。

## Trade-offs / Consequences

- 需要为不同事实设置不同 TTL：订单绑定可较长，物流事实必须短，退货原因随订单作用域清除。
- 不保存所有聊天内容会牺牲部分自由对话连贯性，但避免模型摘要污染业务事实、陈旧状态复用和跨订单串线。
- 旧 SQLite 数据以较低置信度标记为 `legacy_migration`，并遵循原更新时间计算有效期，不因为迁移而延长旧记忆寿命。
- TTL 可通过环境变量调整，但缩短会增加重复询问与 Tool 调用，放长则增加复用陈旧状态的风险，需结合业务变化速度和合规要求校准。
- 如果只设置一个会话 TTL，短时效物流事实会被保留过久；如果没有用户纠正优先级与订单作用域，切换订单时可能用旧原因判断新订单，属于业务正确性风险。
